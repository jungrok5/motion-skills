설명 읽기용어집

Lag Verdict를 쓰기 전과 후를 나란히 보여 주는 제품 소개 영상입니다. 지금은 렉 신고가 들어오면 사람마다 자기 경험과 역량으로 데이터를 찾고 AI에게 물어 분석해서, 사람마다 또 실행마다 결과가 달라집니다. 스킬을 만들어도 스킬은 AI가 읽고 따르는 지침이라 같은 스킬로도 해석이 달라질 수 있습니다. Lag Verdict는 조사 순서 · 쿼리 · 기준값을 코드로 고정해 같은 입력과 같은 데이터면 같은 판정을 냅니다. 화면의 인물 · 질문 · 답변 · 수치 · 판정 해시는 예시입니다.

같은 신고를 운영 담당 A, 서버 개발자 B, QA C가 각자 조사합니다. A는 핑 대시보드와 신고 게시판을 보고 네트워크 렉으로, B는 틱 메트릭과 GC 로그를 보고 게임서버 렉(GC?)으로, C는 클라이언트 로그와 재현 영상을 보고 클라이언트 렉으로 봅니다. 같은 사람이 다시 물어도 답이 달라지고(인프라 렉?), 다음 날에는 로그 범위가 달라져 판단을 미룹니다.

분석 절차를 스킬(SKILL.md)로 만들어도 스킬은 AI가 읽고 따르는 안내문입니다. 함수처럼 같은 입력에 같은 출력을 보장하지 않으므로, 같은 스킬을 세 번 실행해도 게임서버 렉 · 네트워크 렉 · 판단 보류처럼 결과가 갈릴 수 있습니다.

Lag Verdict는 조사를 코드로 고정합니다. 입력(프로젝트 · 서버 · 캐릭터 · 신고 시각) → 조회(데이터 소스 5곳, 고정 쿼리) → 확인(확인 항목, 고정 기준값) → 판정(원인 층 · 구간 · 근거) 순서가 항상 같습니다. 스킬이 "서버 틱부터 확인하세요"라고 안내한다면, Lag Verdict에는 tick_p95 > 50ms (10초 이상) → 게임서버처럼 기준이 코드로 들어 있습니다(예시 규칙).

같은 입력으로 세 번 실행하면 세 번 모두 게임서버 렉, 구간 21:14:05–21:14:40(35초)이 나오고, 판정 해시(예시 7f3a·91c2)도 같습니다. 같은 판정이 나오는 조건은 같은 입력과 같은 데이터입니다. 기록이 더 쌓이거나 바뀌면 판정도 그에 따라 바뀝니다.

앞뒤 비교를 세 가지로 보여 줍니다. 조사 순서는 사람마다 제각각이던 것이 client_perf → net_session → server_tick → host_metrics → ops_events로 고정됩니다. 결론은 세 가지로 갈리던 것이 세 사람 모두 같은 판정으로 모입니다. 근거는 "가능성이 있습니다" 같은 수치 없는 답변 대신 층별 수치(틱 최대 210ms, RTT p95 40ms · 손실 0%, 1초 최대 프레임 22ms 이하, 이웃 서버 정상 · DB p99 9ms)와 직전 이벤트(boss_spawn 21:14:03)로 남습니다.

용어 정리

결정론적 분석
같은 입력과 같은 데이터면 항상 같은 결과가 나오는 분석. 조사 순서와 기준이 코드에 고정되어 있어야 한다.
스킬
AI 어시스턴트가 특정 작업을 할 때 읽고 따르는 지침 묶음. 절차를 안내하지만 함수처럼 출력을 고정하지는 않는다.
판정 해시
입력 · 데이터 범위 · 규칙 버전 · 판정 결과를 하나의 값으로 줄인 것. 두 실행의 해시가 같으면 같은 판정이다(영상의 값은 예시).
데이터 소스
판정에 쓰는 기록이 쌓이는 곳. client_perf · net_session · server_tick · host_metrics · ops_events.
확인 항목
층마다 정상 · 이상을 가르는 규칙과 기준값. 영상의 기준값은 예시.
틱
게임서버가 입력을 처리하고 상태를 갱신해 보내는 한 번의 루프. 초당 20틱이면 한 틱의 예산은 50ms.
RTT p95
서버까지 왕복 지연 시간을 줄 세웠을 때 95% 지점의 값.
직전 이벤트
판정 구간 바로 앞에 운영 이벤트 기록에 남은 일. 영상에서는 21:14:03 boss_spawn.
