설명 읽기용어집

운영 중인 PostgreSQL 테이블의 컬럼 이름을 users.name에서 users.full_name으로 바꾸는 과정을, 실제로 보게 되는 파일과 화면(마이그레이션 SQL, 터미널, 테이블 조회, 백필 로그, 복제 지연 그래프)으로 보여 준다. RENAME COLUMN 한 번은 아직 옛 이름을 쓰는 앱 서버를 바로 깨뜨리므로, 추가 → 이중 쓰기 → 백필 → 삭제의 네 단계로 나누어 각 단계에서 앱과 스키마가 서로 호환되게 한다.

왼쪽 에디터에 0042_add_full_name.sql이 타이핑된다. ALTER TABLE users ADD COLUMN full_name text;로 새 컬럼을 nullable, 기본값 없이 추가한다. 터미널에서 migrate up이 이 파일을 적용하고, 위쪽 users 테이블에 full_name 열이 생긴다. 기존 행의 값은 모두 NULL이다.

PostgreSQL에서 nullable이고 기본값이 없는 컬럼 추가는 테이블을 다시 쓰지 않고 카탈로그만 바꾸므로 잠금이 짧다. 그래도 ACCESS EXCLUSIVE 잠금을 잠깐 잡기 때문에, 긴 트랜잭션 뒤에서 기다리지 않도록 lock_timeout을 두는 것이 일반적이다.

앱 코드 UserRepo.ts의 저장 함수에 full_name: u.fullName 한 줄이 추가되고 버전이 v2가 된다. v2는 name과 full_name에 같은 값을 쓰고, 읽기는 아직 name에서 한다.

v2가 배포된 뒤 새로 가입한 두 행은 처음부터 두 컬럼이 모두 채워진다. 기존 행의 full_name은 여전히 NULL이다. 이 단계에서는 v1과 v2가 함께 떠 있어도 둘 다 정상 동작한다.

백필 로그에 1만 행 단위 배치가 차례로 찍힌다. 각 배치는 UPDATE users SET full_name = name WHERE id BETWEEN … AND full_name IS NULL처럼 범위를 나눠 짧게 끝나는 트랜잭션이다. 테이블의 기존 행이 배치가 지나갈 때마다 하나씩 채워진다.

오른쪽 대시보드의 복제 지연 그래프가 중간에 정지 기준(5초)을 넘자, 로그에 pause 줄이 찍히고 백필이 잠시 쉬었다가 이어진다. 한 번에 전체를 갱신하지 않고 배치와 쉬는 시간을 두는 이유는 잠금 시간과 복제 지연을 작게 유지하기 위해서다. 행 수, 시간, 지연 수치는 예시다.

앱이 full_name만 읽고 쓰는 v3로 바뀐 것을 확인한 뒤(name 참조 0건), 마지막 파일 0043_drop_name.sql의 ALTER TABLE users DROP COLUMN name;을 적용한다. 테이블에서 name 열이 사라진다.

삭제를 맨 끝에 두는 이유는, 그 전까지는 어느 단계에서 멈춰도 앱과 스키마가 호환되기 때문이다. name을 지운 뒤에는 v1, v2로 되돌릴 수 없다.

용어 정리

마이그레이션
데이터베이스 스키마를 바꾸는 변경 하나. 번호가 붙은 SQL 파일(0042_…sql)로 관리하고 순서대로 적용한다.
Expand / Contract
스키마를 먼저 넓히고(추가), 앱을 옮기고, 마지막에 좁히는(삭제) 방식. 단계마다 옛 앱과 새 앱이 모두 동작한다.
nullable 컬럼
NULL을 허용하는 컬럼. 기존 행에 값을 채울 필요가 없어 바로 추가할 수 있다.
이중 쓰기 (dual write)
옮기는 동안 앱이 옛 컬럼과 새 컬럼에 같은 값을 쓰는 것.
백필 (backfill)
새 컬럼이 생기기 전부터 있던 행을 옛 값으로 채우는 작업. 작은 배치로 나눠 실행한다.
복제 지연 (replication lag)
복제본(replica)이 주 서버의 변경을 따라오지 못하고 뒤처진 시간. 대량 갱신 때 커진다.
ACCESS EXCLUSIVE 잠금
ALTER TABLE이 잡는 가장 강한 테이블 잠금. 잡혀 있는 동안 그 테이블의 읽기와 쓰기가 기다린다.
lock_timeout
잠금을 기다리는 최대 시간. 넘으면 문장이 실패하므로, 마이그레이션이 다른 쿼리를 오래 막지 않는다.
